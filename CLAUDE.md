# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## ⚠️ Next.js version warning

This project pins `next@16.2.6`, a version with breaking API/convention changes relative to training data. **Before writing any Next.js code** (routing, `route.ts` handlers, config), check `node_modules/next/dist/docs/` for the current API — do not assume App Router conventions from memory are still correct.

## Commands

```bash
npm run dev      # Start dev server (http://localhost:3000)
npm run build    # Production build
npm run start    # Run production build
npm run lint     # ESLint (flat config in eslint.config.mjs)
```

There is no test suite configured in this repo.

### Local dependencies for running the app

- A running LiveKit server (`livekit-server --dev` or the Docker image — see README.md).
- `.env.local` with `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, `NEXT_PUBLIC_LIVEKIT_URL`, `LIVEKIT_URL`, `GEMINI_API_KEY`. Optional: `TRANSLATION_MODE=dual` (see below; default `hybrid`), `HYBRID_AUDIO_LANGUAGE` (initial voice language, default `th`), `TEXT_TRANSLATE_MODEL` (default `gemini-3.5-flash-lite`), `NOISE_FILTER=off` disables the server-side noise gate. `SILENCE_SAVER=off` makes bridges stream audio to Gemini continuously instead of pausing during silence, which is useful for A/B cost tests. `INTERIM_TRANSLATION=off` turns off the hybrid in-progress text translations (see below). `POLISH_TRANSLATION=off` turns off the correction of Live-translated Thai (see below). `ENGLISH_TERMS=off` keeps Thai originals exactly as Live transcribed them (see below).

## Architecture

This is a Next.js App Router app that bridges a LiveKit room to the Gemini Live API to provide real-time spoken-language translation for live broadcasts.

**Core flow:** an organizer publishes mic audio into a LiveKit room → a server-side bot (`TranslationBridge`) joins that same room per requested target language, subscribes to the organizer's audio, streams it to a Gemini Live API WebSocket session configured with `translationConfig`, and republishes the translated audio back into the room under a `translator-{lang}` identity. The watch page is a **two-way interpreter** (default TH ⇄ EN): it subscribes to one bridge per column language. Because `translationConfig` is one-directional, the `en` bridge carries Thai speech and the `th` bridge carries English speech. Every bridge requests `inputAudioTranscription`, and the client keeps an utterance only when its script-detected source language (`detectLanguage` in `languages.ts`) differs from the bridge's target. Each utterance therefore appears once, with its original and translation taken from the same Gemini session; never pair text across bridges, because independent sessions segment turns differently. Audio is optional, and `setSubscribed()` picks which track (if any) the attendee hears.

**Hybrid mode (default, `TRANSLATION_MODE=hybrid`):** for `DEFAULT_PAIR` (TH/EN), only the session's *voice language* gets a Live session. It starts as `HYBRID_AUDIO_LANGUAGE` and the organizer can switch it on the broadcast page (`POST /api/sessions/[id]/audio-language` → `TranslationSessionManager.setAudioLanguage`). A switch starts the new bridge, hands it every subscriber (the counts carry over and the text targets flip), then stops the old one. Hybrid subscribe, unsubscribe and switch calls are serialized per session (`withHybridLock`). The watch page decides which voices exist from the `translator-{lang}` participants in the room, not from the subscribe response. A request for the pair's other language is served as text by that same bridge (`TranslationBridge.textTargets`). When a segment in the bridge's own language ends, `finalizeSegment()` translates it with a text model (`src/lib/text-translator.ts`). It publishes the result under segment id `${target}~${lang}-${bridgeTag}-${n}` with `language: target`. The per-instance `bridgeTag` keeps a re-created bridge from colliding with segments clients already hold. The watch page treats it like any other bridge's output. Its originals are mirrored live while the speaker talks, and while the segment is still open `translateInterim()` re-translates the text so far (throttled; requests may overlap, and an older result than the one on screen is dropped) as a non-final `replace` chunk; results for a segment that has already been finalized are dropped, so the final translation always wins. The text-model timings (interim interval, polish settle, request timeout) assume a paid Gemini key: a free-tier key's 15 requests/min run out in a two-way conversation and translations get lost. If the segment closes with exactly the text of the latest interim request, the final reuses that request's result instead of asking again, and text that ends on a firm sentence end is translated at once for that reason. Own-language segments also end automatically at sentence ends (`src/lib/sentence-boundary.ts`: terminal punctuation, or Thai final particles such as ครับ/ค่ะ/ไหม, since Thai is transcribed without punctuation; past `MAX_SENTENCE_CHARS` run-ons break at a space, or before the chunk for unspaced Thai, rather than waiting for the 20 s cap). A chunk that contains a sentence end is split there, the segment advances, and the head is translated at once. A segment that ends on a firm sentence end (ครับ/ค่ะ/คะ or `.?!`) closes after `SENTENCE_END_GAP_MS` of quiet instead of `SEGMENT_GAP_MS`. Thai chunks arrive about a second apart, so a break is held when a trailing particle follows or may still be arriving ("…ไหม ครับ"). Live-translated segments are not split on the original side, because their translation lags the original and late chunks would attach to the wrong segment. Instead, `liveSentenceSplit()` closes the row when a *translated* chunk completes a sentence (`lastSentenceEnd()`) and the original has a `.?!` end (`lastPunctuationEnd()`) within its last two chunks (`originalChunkStarts`); an earlier end means the translation caught up with a sentence the original hasn't ended yet, and cutting there left the question in a row with no translation. By then the original sentence it renders has ended, since the translation lags about one chunk. Original text past that end ("How" of the next question) is moved to the next row: the old row's original is re-published as a `replace`. Rows otherwise close on the original-chunk gap (`SEGMENT_GAP_MS`) or the 20 s cap. A speaker change with no pause also starts a new segment (`switchesLanguage()`): a clean Thai chunk after pure English that ended a sentence or runs to 4+ words, or a clean English chunk after Thai that is a clause (`isEnglishClause()`: it has English grammar words, or is a capitalized sentence). English terms on their own ("terminal manager", "override") stay in the Thai row: split off, they went to the Live translation and came back translated. Joined together, a Thai reply could tip an English row's majority language to Thai and hide the whole row. Gemini Live translates piece by piece, so its Thai can lose meaning, mix pronouns and particles, or garble numbers, and its transcription arrives as unspaced fragments. The live-translate model sends no `turnComplete`, so a Live segment can stay open until the next utterance. A Live segment into Thai is therefore corrected by `refineTranslation()`, sentence by sentence (`LiveRefine` state in the bridge). As soon as the draft completes a sentence (`lastSentenceEnd()`: ครับ/ค่ะ/`.?!`, not คะ, which also ends clauses inside questions), only the new sentences are sent. The already-corrected Thai goes along as context, and the English is cut at its last sentence end (`untilLastSentenceEnd()`); given English beyond the draft, the model translated into it and the next correction repeated that part. While the English has no sentence end yet (Live often puts ครับ after "Good morning,"), the mid-segment correction waits. A result that opens with the already-corrected Thai has it stripped (`withoutRepeat()`). The rest is corrected once the translation has been quiet for `POLISH_SETTLE_MS` (2 s, longer than the ~1 s between Live chunks) and when the segment closes. The row is published as a `replace` of "corrected so far + raw rest", final when nothing raw is left. Later Live chunks append to it. One request runs per segment at a time; a trigger that arrives meanwhile runs again afterwards, so no result is thrown away. Throwing results away whenever more translation arrived, which used to happen, meant continuous speech got no correction until the speaker stopped. A Live segment is final only through this path; with refine off or failing, the raw text is published final on close. Segments whose source is already Thai are skipped, because the watch page hides them. The refine prompt changes the draft only where it is wrong or doubtful compared with the English, makes no sense or reads oddly, or doesn't fit together (mixed pronoun and particle). Everything else keeps the draft's wording, since the audience hears the draft as audio. Speakers mix Thai, English and English spelled in Thai, so each word keeps the language and spelling it has in the draft. No word is moved into the other language, and new wording is written in Thai. The prompt deliberately leaves out `DOMAIN_PROMPT`, whose "keep English terms" rule made the model swap correct Thai for English. It also names no example terms, because doing so primed the model to produce them. Refine uses its own `REFINE_MODEL` (`gemini-3.1-flash-lite`, not `TEXT_TRANSLATE_MODEL`), which is faster and never spaced every word in testing. If a result moves words into the other language (`languageSwaps()`: English the draft lacks, except capitalized codes the speaker said, or English the draft has that went missing; about 15% of results), it is asked once more, naming those words. A result is dropped, and that part keeps the Live text, if it still swaps, if it spaces every Thai word (`spacesEveryWord()`), or if it is over 1.5× the length of its draft piece (it ran past the draft). `NUMBER_RULE` in `interpreter-prompt.ts` makes every path write numbers as digits, with separators for amounts and plain digits for IDs. It is part of `DOMAIN_PROMPT` and of the refine prompt. `DOMAIN_PROMPT` also has `NUMBER_DETAILS`: digits for small counts and durations too, and Thai Buddhist years turned into Western years going into English. The text path also converts those years in code before the model sees them (`westernYears()` in `src/lib/thai-year.ts`), because the model's own subtraction produced wrong years; the display keeps the original. A finished Thai original gets its English words back in Latin letters (`restoreEnglishTerms`, `src/lib/english-terms.ts`), because Live's transcription spells everyday ones in Thai ("คอนโทรล") and neither `languageCodes`, `customVocabulary` nor the system prompt changes that. The text model only names `thai => english` pairs and code does the swap, after a check that the Thai sounds like the English (`soundsLikeEnglish`), so the rest of the text can't change. The row's original is re-published as a `replace`, under the text target's id or, for a Live translation of Thai, the bridge's own; the translation doesn't wait for it. A result that would make the text mostly English is dropped, since the watch page would hide that row. `DOMAIN_PROMPT` is written for an internal audit of LRT (Laemchabang International Ro-Ro Terminal, Terminal C0 at Laem Chabang Port), and its comments record which wordings were measured to cause errors, so re-test a change with 10 runs per sentence. The reason is cost, measured against the API: the live-translate model ignores `responseModalities: ["TEXT"]`, always outputs audio, and for same-language speech emits billed *silent* audio. So a second Live session paid double input plus wasted output. That silence depends on the prompt: told to translate "between Thai and English", Live ignored `echoTargetLanguage: false` and spoke over Thai speakers on the Thai voice, sometimes in English. So Live sessions use `liveDomainPrompt()`, which names one direction and leaves the text path's `DOMAIN_PROMPT` as it was. Live can still repeat scraps with no transcription, so audio plays only within `TRANSLATED_AUDIO_HOLD_MS` of a translation chunk, whose text arrives ahead of its audio. A Thai sentence that opens with English can still get repeated in Thai, because Live treats it as English; muting by source language was rejected because it cut the end of a translation when someone replied at once (57% of its audio left). Use `dual` for audio in both directions. Domain and glossary instructions shared by both paths live in `src/lib/interpreter-prompt.ts`.

### Key files

- [src/lib/translation-bridge.ts](src/lib/translation-bridge.ts) — `TranslationBridge` class. One instance per (session, language). Owns the LiveKit bot participant, the Gemini WebSocket, and the audio pipeline in both directions. Handles Gemini reconnect-on-GoAway, and serializes `AudioSource.captureFrame()` calls via a promise chain (`captureChain`) to avoid frame pile-up in the `@livekit/rtc-node` FFI layer. Transcriptions are sent over LiveKit's reliable data channel (`publishData`, topic `"transcription"`), independent of audio subscription state.
- [src/lib/translation-session-manager.ts](src/lib/translation-session-manager.ts) — `TranslationSessionManager`, a process-wide singleton (`getInstance()`). Enforces **at most one Gemini Live session per language per room**, ref-counts subscribers per bridge, and tears down a bridge (closing the Gemini WS and disconnecting from LiveKit) when its subscriber count hits zero. Because this is an in-memory singleton, the deployed service **must run as a single instance** (see `--max-instances 1` in README's Cloud Run deploy command) — do not introduce code that assumes multiple Node processes can share session state without first replacing this with an external store.
- [src/lib/languages.ts](src/lib/languages.ts) — static list of `SUPPORTED_LANGUAGES` (code/name/nativeName/flag/script regex), `DEFAULT_PAIR`, and `detectLanguage()` (script-count source detection; a quarter Thai letters makes text Thai, because the English terms in a code-switched Thai sentence outnumber its Thai letters). Codes are valid `targetLanguage` values for the Gemini `translationConfig`. `SUPPORTED_LANGUAGES` is the only list of languages that get translated: `isSupportedLanguage()` gates the `/api/translate` routes (400) and `TranslationSessionManager.subscribe`/`createBridge` (throws `UnsupportedLanguageError`), and the bridge's source-language prompt and `HYBRID_PAIR` derive from it. A commented-out entry (e.g. `ja`) is switched off everywhere.
- [src/lib/audio-filter.ts](src/lib/audio-filter.ts) — `NoiseFilter` (100 Hz high-pass + adaptive noise gate with hold) applied to organizer audio in `TranslationBridge.sendAudioToGemini`. Its `gateOpen` state also drives the bridge's **silence saver**, because Gemini bills input audio per second, silence included. After 1.5 s of silence the bridge stops sending audio, which is longer than the VAD's 800 ms, so the turn has already ended; it also sends `audioStreamEnd`. When speech resumes it sends a 300 ms pre-roll of *unfiltered* audio first. The gate's output is silence while it is closed, so a filtered pre-roll used to cut the first syllable. After 3 min with no speech and 15 s with no Gemini output, it closes the Gemini socket (the LiveKit bot stays) and reopens it on the next speech. Audio is buffered in `pendingAudio` while connecting and flushed in order, so nothing is lost. Keep these invariants if you touch it.
- [src/app/api/sessions/route.ts](src/app/api/sessions/route.ts) and `[sessionId]/route.ts` — create/list/delete broadcast sessions (delegates to `TranslationSessionManager`).
- [src/app/api/translate/route.ts](src/app/api/translate/route.ts) — `POST` requests/reuses a `TranslationBridge` for a language (and unsubscribes from a `previousLanguage` if the attendee is switching); `DELETE` unsubscribes. `targetLanguage === "original"` is a special case meaning "no translation, listen to organizer directly."
- [src/app/api/token/route.ts](src/app/api/token/route.ts) — issues LiveKit access tokens; `role=organizer` grants publish, attendees are subscribe-only.
- [src/app/session/[id]/broadcast/page.tsx](src/app/session/[id]/broadcast/page.tsx) — organizer UI (publishes mic audio, shows QR code via `src/components/SessionQRCode.tsx`).
- [src/app/session/[id]/watch/page.tsx](src/app/session/[id]/watch/page.tsx) — attendee UI: split-screen subtitles (`components/SplitTranscript.tsx`, where `buildRows` holds the source≠target filtering), bridge subscriptions (`hooks/useTranslationBridges.ts`, which owns subscribe/unsubscribe/beacon cleanup), the transcription data channel (`hooks/useTranscripts.ts`), audio choice, light/dark theme and fullscreen. Cell text goes through `formatTranscript()` (`src/lib/text-format.ts`: spacing after punctuation, Thai comma/full stop → space, spaces around English words in Thai, a space after ครับ/ค่ะ). Filtering still uses the raw text. The latest row is the "current" utterance: it is shown larger, and `LiveText` highlights each newly arrived chunk. The reader can resize subtitles (`--font-scale`, A−/A+ or the +/− keys) and hide one column; both preferences are kept in localStorage. The header's download button (`components/TranscriptDownload.tsx`, builders in `components/transcript-export.ts`) saves the session as `.txt` or `.docx` (the `docx` package, imported on demand), from the same `buildRows` rows. It reads an uncapped copy of the groups that `useTranscripts` keeps (`getTranscript()`), because the on-screen list holds only the last `TRANSCRIPT_CAP`. Word ignores a `cs` font, the document defaults and the theme's Thai font for Thai text, and draws it in Angsana New; so Thai gets runs of its own with every font slot set to Tahoma.

### Design constraints worth knowing before changing things

- **Audio only**, no video — intentional, for bandwidth/simplicity.
- Uses Gemini's native `translationConfig` (directional translation), not a prompt-based approach — don't replace this with prompt engineering without discussion.
- The bot joins via `@livekit/rtc-node` (server-side native bindings), not a browser client. Its native layer drops a room if JavaScript doesn't acknowledge the connect quickly. The symptom is `handle not found (… ReadyForRoomEvent …)`, which happens often under `next dev`'s slow event loop and was never seen under `next start`. `TranslationBridge.connectRoomWithRetry` handles it: it retries, serializes joins across bridges, and keeps failed `Room`s referenced. That last part matters because garbage-collecting a dead native handle throws an uncaught "trying to drop an invalid handle".
- Gemini Live outputs 24kHz mono PCM; input to Gemini is resampled to 16kHz (the rate the live-translate model expects) by rtc-node's `AudioStream` — sample rates are hardcoded in `TranslationBridge` (`sampleRate` / `inputSampleRate`) and the `AudioStream` rate and the `audio/pcm;rate=` mimeType must stay consistent.
- Tab close cleanup relies on `navigator.sendBeacon()` on `beforeunload` to call the unsubscribe endpoint and let idle Gemini sessions get torn down — don't assume normal fetch-based cleanup will fire reliably on tab close.
- Current architecture is single-room / single-process and documented in README.md as a "demo" design with known scaling limits (O(n) signaling fan-out, single-process Gemini connections). A 3-tier (ingestion/translation/delivery rooms) design is described there as the recommended path for 100+ attendees or 20+ languages — read that section before making scaling-related changes.
